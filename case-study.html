CyberAgent

A classifier labels malicious network flows. An agent then investigates a flagged flow with five fixed tools and writes an assessment — and a verifier audits that assessment line by line against the evidence the tools actually returned. On top of it sits a security-operations console: an endpoint agent, an alert intake with a queue and a circuit breaker, a deterministic correlator, an analyst-feedback loop that can train and promote a candidate model, a knowledge pack with BM25 retrieval, Sigma rules replayed against the corpus before they may be exported, and a dry-run response planner with an approval queue.

The design rule that runs through all of it: no number appears unless a stored artifact produced it, and a refusal is rendered as a refusal rather than as an empty screen.

This link is a static build with no backend behind it. There is no API here, no database, no model file and no credential — the operator key that authorises the platform's 31 routes exists only in the owner's local .env and is attached by a dev server, so a published copy of the frontend cannot reach it. What it can do is replay one. The six operator screens that talk to the API read a recording of one real localhost run: scripts/capture_fixtures.py populated a scratch store through the same routes the browser uses, wrote each answer out byte for byte, checked every recorded filter against the live server before keeping it, and replaced the machine-identifying values with synthetic ones. The other five keep the badges they already had — Demo data, Demo fixtures, Simulated — not live traffic — because they were never reading the API in the first place. The zero-day holdout, kept visible

47 flows of two classes no supervised model here has ever seen — Heartbleed and Infiltration. All 47 were predicted BENIGN. Accuracy 0.0 and macro F1 0.0 for all five models. A supervised classifier cannot label a class outside its label set, and the artifact records that rather than hiding it.

What the artifact itself says about these numbers

  • Held-out CIC-IDS2017 split; day-to-day drift means these numbers are not real-world generalisation.
  • Severe class imbalance (BENIGN dominates), so accuracy overstates attack performance; macro F1 and per-class metrics are the load-bearing numbers.
  • The split was stratified at random per flow rather than by capture day, so same-day near-duplicate flows can appear in train and test.
  • Per-sample predicted probabilities and split indices were not persisted; regenerating them requires re-running preprocessing and evaluation.
  • Precision-recall curves are for the selected best model only.

The console, and what decides each step

Nine stages, each with a rule that names the constant behind its output. The two load-bearing choices: no model and no LLM decides the grouping or the response, and the classifier's label is never overridden by the narrative.

1 · Endpoint agentA Wazuh-style agent observes logs, processes, the network table, file hashes and inventory, and POSTs to the manager. No inbound listener, no command channel. 49 detection rules in 7 YAML files, levels 0–14; a rule whose field is not in the readable vocabulary is refused at load.
2 · Classify & triageFlows through the selected model; severity comes from a fixed class–severity table, not from a learned score.
3 · Intake & queueOne write door: provenance check, dedupe by content hash, store, triage, enqueue. Leased workers, an attempt budget, stale-lease recovery, a circuit breaker, and 100 jobs per request as the hard cap.
4 · CorrelateEntities are host:, ip:, user: only; wildcard addresses correlate nothing. Union-find over link keys, a stable inc-… id. Severity = weight × alert count × mean confidence × (1 + duration/3600), escalation only against the archetype floor.
5 · Investigate & verifyFive fixed tools, MAX_TOOL_CALLS = 6, re-reading and re-scoring the stored row before any tool runs. The verifier audits 6 claims on a flow subject and 11 on an incident subject, and the investigation adds a line naming exactly why no LLM answered.
6 · Analyst feedbackA verdict is data: it never mutates a stored label. A confirmed verdict takes the dataset label, never the model's prediction, so a wrong prediction cannot be baked back in.
7 · Retrain & promoteGuards before any training (5 verdicts minimum, 25 per class, a 5% relabel share, 5,000 scanned). The train split is re-labelled, never extended; the test split is never touched. Promotion re-derives the gate from the candidate's own confusion matrix at a 0.002 tolerance.
8 · Knowledge & rules56 MITRE techniques in a hand-curated offline pack; retrieval is BM25, in-process, no embeddings, no network. A Sigma rule is generated only from values a stored row carries, replayed against 389,616 labelled flows, and export is refused while the row is not validated.
9 · Respond (dry-run)DRY_RUN is the only mode and it is not a setting. The module holds no firewall, router, EDR or ticketing client and no credential for one; a test reads its source and refuses the moment an outbound-capable import or call appears.

What is not true here

Every one of these is a recorded limitation, not a claim this page works around.

  • No live LLM. Both configured backends — an OpenAI-compatible endpoint and Ollama — refused the connection when measured, so the backend is mock. Every investigation to date is the deterministic report with the reason named in its limitations, and live-LLM narrative quality is unbenchmarked.
  • The SQL legs have never run. PostgreSQL is present but unusable without a password, so rows fall back to in-memory repositories, GET /health answers degraded, and every table added since Phase 1 has never been exercised against a real server.
  • The platform itself is not deployed. What is published is a recording of one localhost run of it: no API, no store, no model file and no credential ever left the owner's machine. In-memory rows live only as long as the process that made them, so a freshly started API here reads empty lists until something ingests — which is exactly why the tape was captured from a process that had already run the whole chain. The platform binds localhost and listens on nothing inbound.
  • A recording is one run, frozen. The six tape-backed screens all read a single scratch-store pass on 2026-10-29, so the counts are that run's counts and never move: correlating again, draining the queue or filing a verdict cannot change them, because a recording has no store to change. The other five do not move either, for different reasons — /model-results renders the synced evaluation artifact, /, /replay and /simulation are bundled fixtures and a browser-side engine, and /investigation has nothing to show a static build. The whole-table aggregates beside a filtered page are whole-table over that run. Machine-identifying values were replaced with synthetic ones before the tape was written, so the hostnames, addresses and account names on these screens are invented; the CIC-IDS2017 flow addresses are not, because they belong to the published dataset.
  • The rule gate is precision-only. The rule generated live from a Bot incident passed with precision 1.0 on one true positive against 1,965 missed ones (recall 0.0005: tp=1 fp=0 fn=1965 tn=387650) and is exportable, while a 27-alert host rule reads precision 0.0 and is refused. Recall is published and never enforced. Three priced alternatives are on record, undecided.
  • Exported rules are unverified by any sensor. exportable: true means "this project replayed it and the numbers agree". No export has been loaded by pySigma or a real Sigma sensor. And a host rule's truth is another rule's verdict, not the machine's state.
  • An analyst verdict can reach 91.27% of the flows. 34,003 of the 389,616 addressable flows (8.73%) never entered the retrain corpus — 33,956 removed by duplicate-row cleaning plus the 47 holdout rows — class-skewed up to 45.4% of SSH-Patator.
  • Promotion has only ever run on a scratch database. The project's own store has never had its active-model pointer moved.
  • Two severity systems disagree, knowingly. The review-policy list predates the severity table, so a DoS Hulk alert reads high severity yet needs no human review. The two-line fix is deferred because it changes analyst workload.
  • The knowledge pack is a hand-curated subset. 56 techniques with paraphrased descriptions, not verbatim ATT&CK; its own provenance block says fetched: false, and technique URLs are derived from the id rather than stored.
  • Host-event purity is 0.4834 for the reason given above, and the frontend has no render-level test suite — no jsdom, no testing-library, no Playwright flow. The screens are proven by typed-client tests, a source scan and a hand pass.
  • There is no React error boundary. A component that throws during render blanks the view; the defensive readers in lib/socView.ts are the mitigation in use, and they only help where a view calls them.

How it actually runs

Three terminals on one machine, and the whole chain is reproducible. There is no make here, so the underlying commands are given. 

# 1. the API (Python 3.13 through uv)
uv run python scripts/tasks.py run-api

# 2. the console - its dev proxy attaches the operator key from .env, so no screen asks for it
uv run python scripts/tasks.py run-ui

# 3. the end-to-end demonstration: enroll, deliver the scripted campaigns, replay 120 flows,
#    run the queue, correlate, investigate, file feedback, plan a dry-run response, decide it
uv run python scripts/run_demo.py --flows 120 --seed 42 --verbose

# the correlation measurement, and the Sigma rule replay
uv run python -m scripts.correlation_benchmark --flows 120 --rate 40
uv run python -m scripts.replay_flows --flows 200 --rate 60 --investigate

# every gate
uv run pytest -q
uv run ruff check src scripts tests
cd frontend && npm test && npm run lint && npm run build

# and, for this published copy: record one run's answers, scrub them, fold-check them, assemble
uv run python -m scripts.capture_fixtures --url http://127.0.0.1:8011
uv run python scripts/build_showcase.py

The scripted attack stories and the flow replay mark every event and every derived alert is_simulated=true. They are training-wheel data for the console, not evidence about any network. The capture refuses to write a filter it could not reproduce against the live route, and the assembler refuses to publish a package that still carries a value identifying this machine.
